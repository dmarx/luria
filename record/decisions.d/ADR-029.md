# ADR-029: A checking job runs nothing that writes, and the remedy says so where it is read

## Context

[ADR-018](ADR-018.md) put two derived counts on the README and made
`luria lint` fail when they drift. The mechanism was fired and works. What it
did not settle — because it never had to be said out loud here — is **who runs
the generator**.

In this repository all three generated view kinds (the index and tag pages, the
devlog books, the badge region) were born committed, so the question never
surfaced. It surfaced in the first project to adopt the badges after the fact.

The adopter did the documented thing: added the `<!-- luria:badges -->` region
to `README.md`. CI went red, correctly, with the message we wrote:

```
README.md: badge counts are stale — run `luria index`
```

They then did what the message said, in the place they were reading it — added
`luria index` to the docs-lint job, one step ahead of `luria lint`. The red
cleared. Three green builds followed with the badge region on `main` still
empty, because the regenerated README lived in a runner checkout nobody
commits.

The badges not appearing was the harmless half. `luria lint` verifies generated
views by re-rendering and diffing against disk, so a generator immediately
ahead of it makes that comparison vacuous — the checker compares the
generator's output against the generator's output. Demonstrated by corrupting a
row of the generated index:

```
luria index && luria lint   → exit 0    (corruption silently overwritten)
luria lint                  → exit 1    docs/decisions/README.md: stale
```

The whole of `check_generated_index` was inert. A pull request adding a
decision without regenerating the index would have passed.

This is the **third** inert mechanism in the project [DP-6](../../docs/design-principles.md#dp-6) was minted from, and
the first one this package caused. The other two were inert from bugs in
themselves; this one was a working gate switched off by the repair for an
unrelated symptom — and, as [DP-6](../../docs/design-principles.md#dp-6) predicts, nobody noticed, because a
check that cannot fail is indistinguishable from one that passes.

The proximate cause is ours. The remedy text is **correct in a working copy and
catastrophic in a checking job**, and nothing at the point of use distinguishes
those contexts. A staleness failure is usually seen *first* in a build log,
which is exactly where the sentence names the wrong action.

## Decision

**A checking job runs nothing that writes.** Regeneration is the author's;
verification is CI's. Stated as a rule in [`docs/adopting.md`](../../docs/adopting.md) rather than
implied by a correct example, because a positive example with no stated
invariant does not make adding a step feel like a violation.

Three changes make the tooling carry it, all in `luria/ci.py`:

- **`regenerate_remedy()` — the remedy knows where it is being read.** In a
  terminal it stays the bare `run `luria index``; padding that with CI advice
  would train people to skim the one message that matters. Under CI it adds the
  two things the short form leaves to be guessed: the fix belongs in a working
  copy and is committed, and adding the generator *here* would stop this check
  from being able to fail. Used by `luria lint`, `luria index --check` and
  `luria badges --check`.
- **`wasted_write_warning()` — a write inside a build says so.** A write whose
  result is discarded at job end looks exactly like one that landed.
- **Bare `luria badges` says it only printed.** It emits markdown and exits 0;
  as a `- run:` step that is indistinguishable from a write, which is why the
  adopter's *second* step also did nothing. The note goes to **stderr**, so
  `luria badges > file` keeps working — [DP-1](../../docs/design-principles.md#dp-1), which the command was
  quietly failing.

Detection is deliberately crude (every CI sets `CI`; the vendor variables are
named so that dropping the generic one doesn't take the advice with it), and it
only ever changes what is **said**, never what is done. A false positive costs
a sentence of advice; a false negative leaves today's behaviour. Nothing here
gates a write or an exit code — which is what makes the crudeness acceptable.

## Alternatives considered

- **Refuse to write when `CI` is set.** The strongest version, and wrong: a
  scheduled job that commits its own output writes in CI legitimately —
  `luria collect --commit` is in this repo's own workflow and in the adoption
  guide. A rule that makes the documented cadence job fail is worse than the
  trap it closes.
- **Detect the inert ordering itself** — have `luria lint` notice that a
  generator ran in the same job. There is nothing reliable to notice: no shared
  state between steps, and inferring it from mtimes or a clean worktree is a
  guess that would fire on legitimate sequences. The honest surface is the
  message, not a detector.
- **Fold `README.md` into `outputs()`** so the ordinary staleness machinery
  covers it and the whole question becomes moot. [ADR-018](ADR-018.md) already
  rejected this and the reason still holds: it would make `is_generated(README)`
  true, and the reference fixer *skips* generated files, so the README's prose
  would silently stop being linted. One exemption plus one exemption is a blind
  spot. It also wouldn't have helped — the ordering, not the region, is the bug.
- **Docs only, no behaviour change.** Cheapest, and it was the first plan. It
  loses because the misleading sentence is a *program output*, read at the
  moment of the mistake by someone who has not opened the adoption guide.
  Documentation that contradicts a message loses to the message.
- **Status quo.** The trap stays armed for the next adopter, and its signature
  is a green build — the failure mode least likely to be investigated.

## Consequences

- Adopters get the warning where the mistake is made rather than where the
  guide is read. The strata-g integration that produced this is fixed, and its
  own decision record cites this one.
- One new module, `luria/ci.py`, and `tests/test_ci.py` covering detection,
  both remedy forms, the write warning, and the two messages a human actually
  reads (the lint's error text and bare `badges`' stderr note).
- The suite runs *in* CI, so `tests/test_ci.py` clears every CI variable in an
  autouse fixture. Without it those tests read the runner's environment and
  invert on GitHub Actions while passing locally. Verified by running the full
  suite both ways: 264 pass with `CI` unset and with `CI=true GITHUB_ACTIONS=true`.
- Fired before trusting ([DP-6](../../docs/design-principles.md#dp-6)), the point of the exercise: a hand-edited
  badge count produces the bare remedy in a terminal and the "do not add this to
  your job" form under `CI=true`, and the corruption test above distinguishes
  the two job bodies. A guard for inert guards that was never fired would be a
  joke at its own expense.
