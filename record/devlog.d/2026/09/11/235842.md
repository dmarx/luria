**The ask was to replace Quartz's graph with strata-g's; the measurement said
don't, so this adds one instead.** The request was straightforward — luria's
sites already render Quartz's `Component.Graph`, strata-g exports a
self-contained interactive graph viewer, swap one for the other. Before
building it, count what the replacement would draw. On this record: **61 typed
edges across 110 scheme documents**, so 52 of them (47%) have any typed edge at
all, with degrees 1–6 — and journal entries, reports and the README have none
by construction. Quartz's local graph is dense on the same pages for a reason
that has nothing to do with the record's semantics: the generated indexes link
every document they list, so the page-link graph is dense everywhere the typed
graph is empty. Replacing would have traded a neighbourhood on every page for
an empty box on most of them. So the lineage graph is an addition, on the 58
pages that have lineage, and `Component.Graph` stays. That deviation from the
literal ask is the main thing to know about this change.

**Half the lineage was invisible until principles resolved to anchors.** The
first working version dropped any neighbour the site does not publish as a page
— a sound rule, since a node that links nowhere is worse than an absent node.
But design principles *are* published: as anchors in one assembled document,
not as a page each. Measured, **50 of 122 typed-edge endpoints on this record
are principle codes**, all of them silently dropped. The fix is not a second
resolver — `doc_refs.wikilink_target(code, scheme.output)` already answers with
the bare `#anchor` when cited from the assembled document itself, which is
exactly the string needed ([DP-4](../design-principles.md#dp-4)). Pages with a graph went from 33 to 58.

**A nested record cannot spell its own URLs.** Each example under `examples/`
is staged by its own config and then mounted at `content/examples/<name>/`.
Its config has never heard of that mount point, so a URL built from the child's
own `base_url` came out as
`https://dmarx.github.io/luria/record/boundaries.d/BOUNDARY-001` — the
`examples/constitution/` prefix missing, every node a 404. Caught by looking at
the staged output rather than by a test; the parent now passes the child a
`url_base` (and the shared asset URL), and an empty string means "explicitly
none" so a parent without a `base_url` yields a child with no graphs rather
than a child confidently spelling wrong ones.

**Absolute URLs are not a style choice.** The viewer only writes an `href` it
recognises as `http(s)` — a relative path is refused outright. That is what
makes `site.base_url` a hard requirement for this feature, and it is why no
`base_url` means no graphs at all rather than graphs whose nodes do nothing.

**The first render was unreadable, and only a browser said so.** Labels were
`CODE — Title` with the real titles. At 300px in a 750px content column they
ran off the canvas and overlapped each other; the picture was worse than the
table it was supplementing. Nodes are labelled with the code alone now — the
record line two lines up states every one of these edges in prose, so the graph
carries the shape and the prose carries the words. Titles are still in each
node's `attrs`. Verified by driving the staged block in a real browser: 14,552
non-transparent canvas pixels, four nodes, three edges, no console errors, and
a click on a node issuing a request to
`https://dmarx.github.io/luria/record/decisions.d/ADR-028` (intercepted, so the
navigation is observed rather than inferred).

**Driving it also found a bug upstream.** The viewer's inspector empty state
said "Click a node to see its data" — on a page where `navigateOnClick` is set,
a click opens the node's page and the inspector never appears, so that was a
promise it could not keep. Fixed in strata-g along with the discovery that
`navigateOnClick` and `legend` had *no test coverage at all*: no export that
app produces sets either, so this was the first consumer to touch them. They
now have browser tests there, driven by editing the exported data island the
way a third-party producer does.

**The viewer is vendored with a content-hash pin**, and the behaviour the pin
protects is tested upstream, not here. A browser is not a dependency this
package will take on to re-check that a canvas draws; what it *can* check is
that the payload it ships is byte-for-byte the one those tests cover
([ADR-016](../../record/decisions.d/ADR-016.md)'s offline-drift rule, applied to a vendored asset). Verified that
the asset actually ships: built a wheel and listed
`luria/assets/strata_graph_viewer.js` inside it, because hatchling's
`packages = ["luria"]` including non-Python files is the kind of thing that is
true until it isn't.

**And then it shipped, and the built site said it was broken.** A manual
`workflow_dispatch` of the Pages workflow on the branch failed — at `deploy`,
which is a one-second environment refusal because GitHub Pages only deploys
from the default branch, and nothing to do with this change. But `build`
succeeded, which meant there was a **built-site artifact** to look at. Every
one of the 58 pages carried a data island whose quotes had been replaced with
curly ones and whose `</script>` had been moved. The feature was dead on the
real site and the local verification had said it was fine, because the local
verification put the block in a plain HTML page and skipped the markdown
pipeline entirely.

**Two causes, and only the first is the producer's fault.** CommonMark opens
an HTML block only when the tag is **alone on its line**; sharing the line
with the data island made the whole thing a paragraph of inline HTML, so the
typographer ran over it. Reproduced in seconds with `markdown-it-py` — a
different implementation of the same spec Quartz's remark follows — and fixed
with two newlines. That got rid of the curly quotes and the relocated tag.

It did **not** fix it. A clean HTML block still fails, because Quartz goes
remark → hast → **preact**, and a script element's text children are escaped
on the way out. Script content is raw text, so the browser never decodes those
entities back: `JSON.parse` throws. Verified by reading the island in a real
browser on a real build — `{&quot;nodes&quot;: […`, `parses: false`,
`mounted: false`.

**The fix came from a probe, not from reasoning.** Four carriers on one page,
built with the real Quartz and read in a real browser:

| carrier | result |
|---|---|
| `<script type="application/json">` island | **FAILS** — entity-escaped |
| JSON in a `data-graph` attribute | OK |
| base64 in the island | OK |
| base64 in an attribute | OK |

An attribute value is the one place HTML escaping round-trips by construction:
whatever a serializer escapes, the parser decodes. strata-g's viewer now reads
either carrier, and this emits the attribute. Base64 was rejected for being
opaque — a reader viewing source should see the graph, not a decode step.

**Verified the whole way this time**: `luria site` → Quartz v4.5.2 → 58 pages,
all 58 attributes parsing as JSON through an HTML parser, then one page driven
in a browser: 7 nodes / 6 edges, the legend rendered, 5,913 opaque canvas
pixels, the empty state reading "Click a node to open it.", Quartz's own
`.graph-container` still on the page, and a click on `ADR-012` issuing a
request for `record/decisions.d/ADR-012`.

**The lesson worth keeping:** a markdown generator's output is not verified
until something has parsed it as markdown. The tests now run a CommonMark
parser, and read the attribute back through an HTML parser rather than slicing
it out of the string — because the round-trip is the claim being made.

**Known limitation, stated rather than discovered later:** the graph does not
follow the site's theme toggle. The viewer paints canvas labels with literal
2D-context colours, so a `var(--light)` would be dropped by half the widget —
CSS custom properties cross a shadow boundary, but a 2D context does not read
them. It is drawn as one dark figure that reads on both Quartz themes. Fixing
it properly needs a re-theme hook in the viewer upstream.
