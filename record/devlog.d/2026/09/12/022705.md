**Both graphs a luria site can show are computed; neither is one anybody drew.**
Quartz's is the page-link neighbourhood, the lineage graph
([ADR-tmpronup](../../record/decisions.d/ADR-tmpronup.md)) is the typed edges — honest, automatic, and neither of them
a picture of what the project *is*. A project that knows its own shape had no
way to say so. `[luria.site] graph` is that way: point it at a strata-g
`Canvas — graph data (JSON)` export and the picture you laid out replaces
`Component.Graph` on every page.

**Replacing is right here and was wrong for lineage, for one reason: density.**
The argument against swapping Quartz's graph for the lineage graph was measured
— 47% of scheme documents have any typed edge, so most pages would have got a
box with nothing in it. A configured graph is the same picture everywhere.
There is no page it is empty on, so there is no page the swap makes worse. And
two graphs stacked above every document's first paragraph is not something
anyone chooses on purpose.

**The strata-g half was a thirty-line plugin, because the plugin kind already
existed.** `Canvas — graph data (JSON)` writes the bare `GraphExportView` that
the webapp and embed formats already inline into their HTML. Bare, with no
envelope and no version marker: the island's shape is already the contract, so
an envelope would create a second shape of the same data and hand every
consumer an unwrapping step. The `exporters` kind meant adding a format was a
file, which is exactly what that ADR was for.

**Two bugs the tests found before a build did**, which is the reversal worth
recording after the last entry. The viewer asset was written only when the
*lineage* count was non-zero, so a project with a configured graph and no typed
edges anywhere got an element and no script to mount it. And `graph` set
without a `base_url` did nothing at all, silently — the viewer is served from
the site root, which needs a site to have a root. Both are now in the staging
report rather than in the reader's empty box.

**A real export is a test fixture, not a hand-written imitation.** The contract
between the two projects is a file format, and a fixture written here to match
what this module expects would pass forever while the two drifted apart. So
`tests/fixtures/strata_g_export.json` came out of strata-g's actual export
dialog, driven through its real UI, and one test does nothing but feed it to
the loader.

**Verified against a real build, and this time that included the picture.**
`luria site` with the key set → Quartz v4.5.2 → the page carries two graphs
(the configured map and the page's lineage), `Component.Graph` is gone from the
layout, the site graph sits above the document's `# ` heading where Quartz's
was, and a click on a spoke issued a request for `docs/decisions/README`. No
page errors.

**Measured rather than guessed: the panel scrolls at the default height.** At
320px the side panel wants 198px and gets 143px, because the stacked layout
caps it at 45%. Nothing is lost — it is `overflow-y: auto` — and raising the
default would cost every page the height to save one scroll. `graph_height` is
the dial for a project that wants it taller.

**Not enabled on this record.** The capability is here and the key is
documented, but which graph luria's own site shows is a picture somebody has to
draw, and inventing one would be deciding for the project what its front door
looks like on every page.
