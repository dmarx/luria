**Two reports off the deployed site, one afternoon apart: the embedded map did
not follow you when you navigated, and every node was labelled with a bare
code.** Both were real, neither was where I would have guessed, and the second
one turned out to be sitting on a strata-g bug that makes the obvious fix
impossible.

**The map did not follow you because Quartz morphs the DOM instead of replacing
it.** Clicking a node in the graph worked — that is an ordinary full page load,
so the custom element is constructed fresh and mounts its data. Arriving at the
same page through any other link did not: Quartz's SPA router fetches the new
document and *morphs* the existing tree into it, so the `<strata-g-graph>`
element survives with a new `data-graph` attribute on it and an already-mounted
graph inside. `connectedCallback` had already fired; nothing fired again. The
element had no reason to look at its attribute a second time, so the previous
page's neighbourhood stayed on screen looking perfectly plausible.

The fix is upstream in the viewer, not here: `observedAttributes` /
`attributeChangedCallback` on `data-graph`, with `render()` tearing the previous
graph down — destroying it, dropping it from the `window.__strataGGraphs`
registry and releasing the `__strataGExport` handle — before mounting the new
one (`strata-g#786`). This record re-pins the vendored asset and its hash.

**Verified against a real build, with a positive control.** Navigating
`ADR-042 → ADR-005` by an ordinary prose link, then hard-reloading the
destination and comparing: with the newly vendored viewer both graphs on the
page match the reload exactly (26 nodes and 6, against an attribute that says 26
and 6) and the registry holds two instances. With the *previously* vendored
viewer, the same script leaves the map at **13** nodes — [ADR-042](../../record/decisions.d/ADR-042.md)'s
neighbourhood, on [ADR-005](../../record/decisions.d/ADR-005.md)'s page — while the attribute beside it says 26, and
the registry has grown to **5** leaked instances. A check that cannot fail on
the old build is not a check.

**The labels were bare codes because the recipe said so — and the fix I reached
for first does not exist.** Step 5 of `docs/graphs/README.md` bound **Label by**
to `code`, with a note claiming it was load-bearing: that merged nodes would
otherwise "inherit the vault node's long title and collide into a paragraph".
The honest correction is that titles are what makes a map navigable at all. A
code is an address; `ADR-001`, `DP-004`, `ADR-093` tells a reader nothing they
did not already have from the URL.

The obvious repair — a computed column that truncates the title with an ellipsis
so the 60-character cut is not mid-word — is accepted by the UI and silently
ignored. strata-g stamps virtual columns onto nodes *after* it stamps labels and
runs its label merge, so binding **Label by** to one falls through to `title`.
The select reads back the value you chose; the canvas never sees it. Filed as
[strata-g#787](https://github.com/dmarx/strata-g/issues/787), and the measurement
that proved it is in the export itself, which carries the computed value in
`attrs.name` and the unrelated `title` in `label`.

**The same investigation killed a claim this repository was making.** Both the
recipe and the changelog said the two layers "merge on filename". They do not.
strata-g's label merge groups by the on-screen LABEL, and the two layers title
the same document differently — the record layer prefixes the code
(`ADR-001: Four layers of record…`), the vault layer reads the bare heading. Of
the 454 nodes, 120 merge (where the two labels coincide by accident: a changelog
fragment's title *is* its timestamp) and **112 documents render as two nodes**.
A computed column stripping the `CODE: ` prefix would make the labels identical
and fold them together, which is exactly the thing `strata-g#787` blocks. The
docs now say what is true and name the bug rather than describing an
architecture the file does not have.
