[ADR-116](../../record/decisions.d/ADR-116.md) had decided the sources stay files and the database is a view. The
owner's response was the other direction: the machinery should operate on
the database, a config item should say so, `luria new` should write a row,
the lint should validate against it, and eventually the markdown tree is
the artifact. This entry is how that was built on top of the export from
the morning, and the three things that went wrong on the way.

## Where to cut

The measurement from [ADR-116](../../record/decisions.d/ADR-116.md) — 150 filesystem call sites, every writer
doing text surgery, every consumer holding a `Path` — turned out to be the
design, read the other way. If a document stays "markdown with
frontmatter, addressed by its path", then nothing downstream of a read
has to change: `field_edit` still edits a line, directives are still found
by line number, findings still say `path:line`, and links still use
`path.name`. What changes is only *where the bytes are* — so the cut is
at the `Path` methods themselves. `read_text`, `write_text`, `glob`,
`rglob`, `exists`, `unlink`, `stat` became `store.read_text(path)` and so
on, and the store decides, per path, whether that is a file or a row.

The rewrite was mechanical — a script over the package, with a backwards
scanner for the receiver expression and a forward one for the closing
paren that knows about string literals — and 29 modules changed in one
pass with no test failing except the encoding guard, which had to learn
that `store.read_text` is where the encoding is named. Twelve `mkdir`
lines went afterwards, once the store made a file's directory itself: the
first `luria new` under SQLite left an empty `record/decisions.d/` on disk
beside the database, which is precisely the two-sources-of-truth wart the
routing exists to prevent.

The rule that made the routing safe: **only a source path is routed.**
Scheme, journal and fragment directories go to the backend; everything
else falls through to the disk regardless. So `store.rglob(cfg.root,
"*.md")` in the site walks both worlds — disk files that are not sources,
plus rows — and the 150 sites did not need to know which kind of path
they held.

## Three things that went wrong

**The listing cache key.** A directory's revision under the file backend
is its mtime, which moves when the set of files changes. My first SQLite
equivalent was `(count, max rev)`. Write A, write B, delete A: count is
one and max rev is one — the same key as after writing A alone — and a
listing cached then would have said A. Fixed with an autoincrement id
that is never reused: `(count, max id, sum rev)`. Two sets with the same
count and the same highest id are the same set, because the only way to
lose a member and keep the highest id is to have had that highest id
already. The test that should have caught it originally asserted
`!= before or True`, which is the kind of test one writes at speed and
the kind that deserves to be noticed in review.

**Activation.** The store cannot ask the config where the sources are,
because loading the config reads `luria.yaml` through the store, and
`current()` is an `lru_cache` that would recurse. So `current()` activates
the store after loading. That was fine until a test wrote a fragment
before anything had called `current()`: nothing was active, the write
went to disk, and `collect` found no fragments. The store now activates
itself on first use, with a thread-local flag so that the nested read
during loading sees no backend and opens the file. "Every command calls
`current()` early" was true and was not a guarantee.

**The site published the export.** `luria export --markdown` defaults to
`build/record`, `luria site` walks the root for `*.md`, and the second
command staged the first command's output — 407 links unplaced. The site
already skipped its own staging directory for the same reason; it now
skips `build/` whole, which is where every luria command writes and what
`.gitignore` already says.

## Firing it on this record

A copy of this repository's record, through the CLI: `luria export --out
record.sqlite` (290 sources, 133 documents), `backend:` appended to
`luria.yaml`, `rm -rf record`. Then `luria lint` — same sections as from
the tree; `luria new adr` — a temporary code filed as a row and nothing on
disk; `luria export` — derived tables refreshed in place, 291 sources
untouched; `luria export --markdown` — the tree written back out under
`build/record`; `luria site` — 117 decision pages staged from rows. The
same run is a test now (`test_this_record_reads_the_same_from_a_database`),
comparing every rendered view and every lint section between the two
backends; the only view that differs is the record page, by the one row
that says `backend.kind`, which is the page doing its job.

The cost is time: about 4 seconds for the lint from the database against
about 3 from the tree. The first version took 5, because the database
side of every `glob` fetched every row and filtered in Python; asking for
rows under the base with `LIKE` brought it down. Point lookups under a
lock will not beat the page cache, and a record big enough to care has
the derived tables to query.

## What git gave for free

Two things do not exist for rows. `luria repair`'s alias retirement reads
a document's previous frontmatter out of `git show HEAD:path` — under
SQLite there is no such thing, and the repair never fires. A migration's
`.git-blame-ignore-revs` entry has no commit to name. Neither is faked;
both are the cost of not having the tree in git, and both are named in
the decision. The fragment collector's ordering, which also came from
`git log`, was the one that could be replaced: the row's id *is* the
filing order.
