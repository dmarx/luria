---
title: 'A vocabulary is a scheme in shorthand'
created: '2026-10-01T18:30:16'
tags: []
---

**The question was hierarchy.** [#298](https://github.com/dmarx/luria/issues/298) proposed union vocabularies, and behind
it sat a bigger ask: can a record express a hierarchical ontology? A sweep of
the code, the decisions, the docs and the issues found nothing. `groups:` is
a single level, a group is not a value anyone can tag with, and nothing rolls
up. A union would have added composition (one field accepting a cat or a
dog) but not subsumption: "cat" would still not be a term.

**The experiment that settled it used records, not config.** A `TERM`
scheme with a `broader`/`narrower` converse, a chain over `broader`, and
notes citing terms through a reference rendered Pet → Cat → {Tabby, Calico}
as a tree. It refused a citation of a term that did not exist, and gave
every term a status. So the hierarchy was already expressible; what the
record lacked was the move from vocabulary to scheme. The owner's reading:
a vocabulary is a tiny constrained scheme, and a record that wants more from
one is showing a type error, so the mechanism to build is promotion, not a
richer vocabulary ([ADR-tmppzon2](../../record/decisions.d/ADR-tmppzon2.md)).

**The trap was the views.** Hand-converting a vocabulary in a scratch
record linted clean and silently lost two things:

- **Index grouping.** The index could group only by a `fields:` entry, and
  `axis` refused a reference. Nothing listed which RFCs were in an area any
  more, except the published site's backlinks.
- **The old pages.** `docs/rfcs/area/runtime.md` was left behind. The
  directory stopped being one the generator owns once the field stopped
  being grouped, so `luria index` neither rewrote nor removed it, and
  nothing reported it.

The first is now `group: true` on a reference (and `axis` may name one), so
promotion keeps its views. Promotion keeps the field grouped, which makes
the second a non-issue for promotion. It remains a gap for any field that
stops being grouped by hand.

A converse listing each term's members was the cheaper alternative, and was
rejected. It needs no index change, but it makes every tagged document edit
its term's file, which turns popular terms into merge hot spots ([DP-2](../../record/principles.d/DP-002.md)).

**Things found on the way:**

- **The migration scaffold was still TOML.** `luria new migration` wrote
  `title = "…"` into a `.yaml` file that `luria migrate` reads with
  `yaml.safe_load`, where it parsed as one string. A test pinned the TOML
  spelling, so the suite had been enforcing the bug. The scaffold is YAML
  now, and a test parses its commented examples into operations the
  planner knows.
- **A dry run swept for nothing.** It walked every tracked file even when
  the plan had no code renames, which also made it need git. It now skips
  the walk unless there is something to sweep.
- **`modeling.md` still pointed at `statuses.yaml`.** Its "smells" section
  named the file — another stale mention of it, found after
  the second review. Grepping for the vocabulary of a stale claim is what
  finds them, and reading the flagged line is not.
- **The decision-shaped template leaked into promoted terms.** With no
  `_template.md`, `new_scheme_doc` falls back to a form that seeds
  `tags: [record]` and "Why this needed deciding" prose. Promotion now
  writes the scheme's template and stub the way `luria init` does, drops
  the seeded `tags`, and uses the value's blurb (or a provenance line) as
  the body.
