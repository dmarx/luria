**[#331](https://github.com/dmarx/luria/issues/331), and why the existing guard missed it.**
`test_a_fresh_default_init_lints_clean` runs `init`, `index` and `lint`. But
`lint.run()` only raises on violations, so warnings passed it, and three of
them printed on every new record. The new test (`tests/test_fresh_init.py`)
captures what `lint` prints and requires nothing but the all-clear. It covers
the default config and a custom one with no principles scheme, which is the
shape the RFC tutorial uses.

**CLAUDE.md was a copy, not a plan.** `docs/README.md` has been planned from
the config since [ADR-048](../../record/decisions.d/ADR-048.md). `CLAUDE.md` was copied verbatim, and its first
paragraph links `docs/design-principles.md`. In a record with no principles
scheme that link points at a page nothing will ever generate, and
`broken-targets` said so on day one. The paragraph now follows the config.
It points where a document-rendered scheme writes `paths.design_principles`,
and is left out when no scheme does. The broken links seen *before* the
first `luria index` are a different matter: those pages are generated, and
`init` already says to index before linting, so that state is expected.

**`spent-upgrades` was talking to the wrong reader.** Its own devlog entry
(2026-09-06) describes it firing on luria's record "the moment its own
upgrade ran, which is the guard working". The remedy it names, "remove it at
1.0.0", is a change to luria. A downstream record can't make that change. A
record born on YAML never needed the upgrade at all, so for its owner the
row could only teach them to skim past a finding.

Two narrower fixes didn't hold up:
- **Look at git history** for a `luria.toml` the record once had. Both this
  checkout and CI's are shallow, so the answer would depend on clone depth.
- **Have `init` write a `mute` line.** `init` never overwrites a
  `luria.yaml`, so the tutorial path, where the config is written first,
  wouldn't get it.

What does hold is scoping by who can act. The finding is reported only when
the running `luria/upgrade.py` lives inside the record's root, which is true
for luria's own checkout because CI installs it editable (`pip-spec: -e .`).
Along the way: `spent_upgrades()` runs one plan (the statuses one) for every
entry in `SUNSET`, so the `yaml` row has never been checked on its own. That
is unchanged here.

**`collect` crashed on the directory `init` had just made.** The default
`record/changelog.d` has a target, `CHANGELOG.md`, that nothing wrote.
`init` now writes each fragment directory's target with a heading and the
insert marker. `collect` still refuses to create a missing target itself:
what goes above the marker is a choice about the file. But the refusal is
now a message that names the file and says `luria init` writes it, instead
of a `FileNotFoundError`.
