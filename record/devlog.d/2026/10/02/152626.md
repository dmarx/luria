**[#240](https://github.com/dmarx/luria/issues/240).** The duplicate-key half of `frontmatter_shape` compared the raw text before the first colon, on unindented lines only. That approximates YAML without being YAML: `"title":` after `title:`, and any repeated key in a nested mapping, both collapsed silently. That is the [#164](https://github.com/dmarx/luria/issues/164) defect again in other spellings. The check now loads the block with a `SafeLoader` subclass that refuses a repeated key in any mapping, so the parser that does the collapsing is the one asked. The `<!--` half stays a text check, because no loader raises on a key that happens to read `<!--`.

Two details the issue's sketch did not cover:
- **`<<` merge keys** are skipped. An explicit key after a merge is how YAML spells an override.
- **The line number** comes free from the key node's mark, so the finding names it. The issue had expected to lose it.

**Journals were never checked.** `check_journals` parsed frontmatter but never called the shape check, so a devlog entry could pass the lint and still fail the Pages build. It now runs the same check, and still reads its metadata through the cached `read_document`.

**Fired once on a real case.** The issue's repro (`"title": dup` above `title:` in [ADR-124](../../record/decisions.d/ADR-124.md)) and a nested duplicate in a real devlog entry were both reported with the right lines, then reverted. This record lints clean under the stricter check. Lint time: 5.8s against 5.4s on `main`, using the C loader where it is built.
