[#160](https://github.com/dmarx/luria/issues/160) asked for `scheme:` to take a list. The change is the decision in
[ADR-tmp6p6tv](../../record/decisions.d/ADR-tmp6p6tv.md); this entry records how it was checked and what turned up along
the way.

**Fired before trusting.** On a scratch copy of `examples/constitution`,
`BOUNDARY-003` was given `overrides: [PRACTICE-010, BOUNDARY-001]`:

- With the shipped `scheme: PRACTICE`, the lint reported `overrides:
  BOUNDARY-001 is not a PRACTICE code`. That is the failure [#160](https://github.com/dmarx/luria/issues/160) described,
  reproduced.
- With `scheme: [PRACTICE, BOUNDARY]`, the lint exited 0.
- With the edge changed to `VALUE-001`, the lint reported `is not a PRACTICE
  or BOUNDARY code — a BOUNDARY document's overrides names a PRACTICE or
  BOUNDARY document`. The union is checked, not just widened.

None of the example's three boundaries actually overrides another, so the
committed example widens the declaration and leaves the documents alone.
Inventing an edge to show the feature off would have put a false claim in a
worked record.

**Where single-scheme assumptions lived.** The sites that read a reference's
target were found by grepping `.scheme`, `.reference` and `ANY_SCHEME`,
not by following failures, because several would have kept passing while
quietly wrong:

- `code.startswith(f"{target}-")` with a tuple target formats as
  `('LIT',)-` and silently matches nothing. It raises no error.
- `field.reference == ANY_SCHEME` against an unconverted string sentinel
  would have stayed False for every field.
- `converse_scheme_of` would have answered with the first target only.

`ANY_SCHEME` became `("*",)` alongside the change, so every comparison is
tuple against tuple. Every consumer goes through `contract.targets`,
`target_of` and `spelled`.

**The converse decomposed cleanly.** `relations.pairs()` now yields one pair
per target scheme. The crossing-pair machinery from [ADR-097](../../record/decisions.d/ADR-097.md) already filtered
each side's reading to the far scheme's documents, so a multi-scheme field
split into independent per-target pairs and the fixer needed no other change.
`edges()` was the one reader that took a single far scheme. It now unions
the far documents and reads the converse back from each target.

**Two test mistakes worth not repeating.** `_config.merged` deep-merges, so
removing a key from the *extra* fragment leaves the base's copy in place. A
test that wants a key gone has to write the whole config. And a converse
that names a third scheme makes that scheme owe the far field. That is the
rule working, not a bug, though it read like one at first.
