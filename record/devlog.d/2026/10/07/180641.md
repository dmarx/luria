title: 'Review fixes: one door for writes, a wheel smoke test, and git as optional'
created: '2026-10-07T18:06:41'
tags: []

A review of the logic-core stack raised three concerns. Fixing them turned
up a fourth problem.

**Stale reads after an in-process write.** The facts cache keyed on
`(path, mtime_ns, size)` and HEAD, and each solve keyed on the facts list's
identity. A same-size rewrite inside one tick of a coarse clock would leave
both stale. The review suggested a `facts.forget()` called from each
writer. The exposure turned out wider than the facts: they are built
through `adr_index.read_document`, whose parse cache has the same key, so
a rebuilt facts list would still read the old parse. The fix is one door.
`luria/writes.py` has `write_text` and `unlink`, and both call `wrote()`.
That drops the path's entries in the parse, number and listing caches. For
a scheme document it also bumps a generation that the facts are keyed on
(and through them every solve) and drops the reference scan. Generated
views do not bump it, so `luria index` does not rebuild the facts between
pages. An AST rewrite moved all 55 `write_text`/`unlink` calls in `luria/`
through it. `tests/test_writes.py` fails on any that comes back.

Two things the rewrite broke, which the suite caught:

- `upgrade.run` had a local list named `writes`, which shadowed the module.
- `wrote()` loaded the config to ask whether a path was a document, and
  `luria upgrade` must never load the config it repairs. It now asks only a
  config that is already loaded. With none loaded, nothing is cached
  against one, so it counts the write.

**The parity harness cannot see this**, because each command runs in a
fresh process. `test_a_rewrite_the_clock_misses_still_reaches_the_rules`
does: it derives, makes a same-size edit through the door, puts the old
mtime back with `os.utime`, and derives again. I sabotaged the generation
key and the parse-cache drop, and it failed as it should.

**Wheel coverage.** The tests run editable, so they read the `.lp` files
out of the checkout. `tools/wheel_smoke.py` takes the interpreter of a
clean environment the wheel was installed into. It checks that `luria`
imports from there, that every program in the source tree ships and loads
through `importlib.resources`, and that the installed CLI lints an example.
With `relations.lp` deleted from an installed copy, it reported
`the wheel lacks relations.lp`.

**The fourth problem: git had become a hard dependency.** The first smoke
run restricted `PATH` to the venv, and `luria lint` crashed with
`FileNotFoundError: git` in the new HEAD baseline code. 0.36.0 runs all of
lint, index, link --fix and reports without git. Every git call in
`facts.py` now goes through `_git`, which returns None when git cannot run,
and that reads as no repository. The smoke test runs the CLI with git and
without.
