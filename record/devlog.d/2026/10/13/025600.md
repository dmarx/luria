[#371](https://github.com/dmarx/luria/issues/371) asks for chains over a derived relation, the follow-on [ADR-127](../../record/decisions.d/ADR-127.md)
left open. The draft decision, [ADR-tmpfdvjo](../../record/decisions.d/ADR-tmpfdvjo.md), went through three shapes
in one session, and the two that lost are worth not re-deriving.

**First: a field list on the scheme.** `composed: {leads_to: [premise_of,
concludes]}` covers claim → inference → claim and nothing else. It is a
path pattern with every feature removed, in a syntax of luria's own.

**Second: queries as clingo rule bodies.** [ADR-127](../../record/decisions.d/ADR-127.md)'s "user-facing queries"
read as user-written Datalog. That fails [ADR-125](../../record/decisions.d/ADR-125.md)'s "rule in the line". It
also lets a user recurse through negation, and takes away luria's ability
to check endpoints or name intermediates. The owner meant *path* queries,
and had suggested Cypher earlier for exactly this. [ADR-127](../../record/decisions.d/ADR-127.md) rejected Cypher
as an engine and praised its patterns, and those two are separable.

**The motivating case** that made path patterns the obvious notation: a
view walking a question through its answers, objections and replies to its
conclusion, as a unit a manuscript could later be composed from. Two
things came out of sketching it, both outside this ADR:

- That view is a tree across schemes, not a chain, so it needs an outline
  view kind.
- Argument acceptance with attack cycles is not stratified: a cycle gives
  several answer sets. It stays out of the pattern subset by keeping
  `WHERE NOT` off variable-length patterns.

**What exists for Cypher → Datalog, surveyed 2026-10-13:**

- **GraphGlot** (`graphglot` on PyPI, 0.14.3, Apache-2.0, pure Python,
  modelled on sqlglot). It parses GQL and Cypher to one AST and transpiles
  only between those, with no Datalog or SQL output. Fired on this ADR's
  patterns: the `neo4j` dialect parsed all of them, plus `*1..`, `{status:
  'Active'}` and `OPTIONAL MATCH`. The `fullgql` dialect rejects the Cypher
  spellings of variable length and negation, and accepts `->{1,}` and
  `NOT EXISTS { MATCH … }`. The AST is the full GQL program tree. The path
  sits under `GqlProgram → … → SimpleMatchStatement → GraphPattern →
  PathPatternList → PathTerm.factors`, which alternates `NodePattern` and
  `FullEdgePointingLeft`/`Right`. Pre-1.0, with releases days apart, so
  pin it.
- **Raqlet** (Shaikhha et al., CIDR 2026) compiles Cypher and SQL/PGQ to
  Datalog through two IRs. It is the real thing, but no public release
  turned up, and it targets Soufflé-style Datalog.
- **grand-cypher** executes a Cypher subset over networkx. Negated
  patterns and `OPTIONAL MATCH` are "help welcome", and it would be a
  second engine.
- **microsoft/openCypherTranspiler** targets T-SQL, and
  **cypher-for-gremlin** targets Gremlin. Neither fits.

So no tool translates Cypher to clingo for us, and luria writes the
lowering whatever parses. Given that, the owner chose a lark grammar of
luria's own over GraphGlot:

- GraphGlot's tree buries the path fifteen wrapper levels deep.
- It accepts all of Cypher, so the subset would need a second pass.
- It is a pre-1.0 dependency.

A scratch grammar was 15 rule lines:

```lark
// A path pattern: the subset ADR-tmpfdvjo admits.
start: path ("WHERE"i "NOT"i path)*

path: node (edge node)*

node: "(" VAR? (":" NAME)? props? ")"   // a bare (c) refers to a node bound earlier
props: "{" prop ("," prop)* "}"
prop: NAME ":" STRING

edge: "-[" VAR? types length? "]->"     -> right
    | "<-[" VAR? types length? "]-"     -> left
types: ":" NAME ("|" NAME)*
length: "*" INT? ".." INT?

VAR: /[a-z_][A-Za-z0-9_]*/
NAME: /[A-Za-z_][A-Za-z0-9_]*/
STRING: /'[^']*'/ | /"[^"]*"/
%import common.INT
%import common.WS
%ignore WS
```

It parsed every pattern and refused
`OPTIONAL MATCH`, undirected edges and `RETURN`. Two gaps for the real one,
both closed in `luria/patterns.lark`: `*..3` now takes Cypher's default
lower bound of 1, and a bare `*` reads as `*1..`.

Its first run caught a rule the ADR had wrong. `WHERE NOT (c)<-…` names a
bound node without a label, so a node needs either a label or a back
reference. The trap for whoever builds it: lark's refusals are "unexpected
token at column N". So naming the out-of-subset construct (`RETURN`,
`OPTIONAL`, an undirected edge) is a check of its own, before or around
the parse.

## Building it

Three things the ADR got wrong or left out, found while implementing it:

- **Direction.** A chain nests the holder of a field under its target:
  `A extends B` puts A under B. A pattern stands in for a field, so its
  first node nests under its last. The ADR's first example,
  `leads_to: (a:CLAIM)-[:premise_of]->…->(b:CLAIM)`, would have hung
  premises under their conclusions. The example now reads backwards on
  purpose (`follows_from: (b)<-[:concludes]-(i)<-[:premise_of]-(a)`), and
  the config docstring says why.
- **A closure stays within one scheme.** Each step of `-[:f*]->` is
  `held/4` on the near node's scheme, so the documents between the ends
  have to be of that scheme too. That became a load-time refusal rather
  than a closure that silently stops after one step.
- **"also extends" ([#359](https://github.com/dmarx/luria/issues/359)).** A step with two premises renders under one
  and names the other with the hard-coded "also extends". On a pattern
  chain that is wrong. [#359](https://github.com/dmarx/luria/issues/359) is an open PR that names each extra parent by
  its relation, so this PR leaves the line alone rather than conflict with
  it.

One trap from writing `examples/argument-map`: a document whose frontmatter
does not parse is all prose to `luria link --fix`, so the fixer wrote
markdown links into the frontmatter lines. The cause was a stray first line
from a shell `printf --`. The lint reported "no YAML frontmatter" first, but
by then the fixer had already run. Check that a new document parses before
running the fixer on it.

Fired on the example before trusting it. `docs/argument.md` shows each step
"through" its inference, and `docs/uncontested.md` drops the challenged
step. The example lints clean.

## Trying it on nucleation

Run on a scratch copy of dmarx/nucleation, with a worktree of `main` beside
the branch:

- **Parity holds.** Unchanged, all 625 files `luria index` writes are
  byte-identical between the two, and `luria lint` is too once
  `lint.network: never` is set in both copies. Run with the network on, the
  outputs differed only in which arXiv identifiers each run got throttled
  on, so compare with the network off.
- **The pattern earns its place.** `argued_from: (c:CLAIM)<-[:concludes]-
  (g:ARG)-[:rests_on]->(p:CLAIM)` on the `argument` chain draws the steps
  through ARG-006, ARG-007 and ARG-008, which a chain over `rests_on` never
  saw. ARG-004 is Rejected and drew a step too, until `WHERE NOT (g
  {status: 'Rejected'})` took it out. A bare back-reference with a property
  map does that, with no new syntax.
- **Built-in open ends failed, and were removed.** The first version listed
  every partial match that could not be completed under *Open* on the chain
  page. On nucleation it listed six arguments, all of them complete: they
  rest only on `grounds`, which nucleation's `premises` field group allows.
  It ignored `WHERE NOT`, so Rejected arguments appeared too. The case it
  was built for, premises and no conclusion, cannot occur there, because
  `ARG.concludes` is required and the lint already catches it. The owner's
  point settled it: what a record calls unfinished is a pattern it can
  write, so luria should not guess. Rendering such a pattern is [#373](https://github.com/dmarx/luria/issues/373).
- A step held both by a field and by a pattern shows "through" only when it
  renders under that parent. CLAIM-027 rests on CLAIM-080 directly and
  through ARG-009, renders under another parent, and so shows no "through".
  Minor, and left alone.
