[#373](https://github.com/dmarx/luria/issues/373) gives a named pattern a page of its matches ([ADR-tmpgicpu](../../record/decisions.d/ADR-tmpgicpu.md)). The
page is a view luria supplies: a pattern with an `output:` adds a view at
load whose template is `luria:pattern.md.j2`, shipped in
`luria/view_templates/`, and the view environment's loader is now a
`ChoiceLoader` that tries luria's own `luria:` prefix before the project
root. The template reads rows through the `match` every view template
calls and writes codes bare, so `linkify` makes the links.

**The first version was a renderer of its own, and the rework deleted it.**
It added `pattern_match/2` to the lowering, taught `logic._python` to read a
clingo tuple, and wrote the table in `luria/pattern_reports.py`. All of
that duplicated `views._Record.match`, which merged to `main` with [ADR-130](../../record/decisions.d/ADR-130.md)
while the branch was open, and then needed its own freshness, exclusion and
error-locating. As a view the page gets all three from existing code, and
the tests that held the first version's output pass unchanged against the
second, link targets included.

Things worth not rediscovering:

- **`match` returned a row per whole match, anonymous nodes included.** Two
  matches differing only in an unnamed node came back as two identical
  rows, which a template cannot tell apart. It now collapses them; the old
  renderer had done the same in its own `sorted(set(...))`.
- **A collision check belongs to the set of renderers, not to the newest
  one.** The first version checked a pattern page against schemes, reports
  and chains, and noted that a chain colliding with a scheme was still
  unchecked. `main` checked no pair at all. `config._check_rendered` now
  gathers every path a renderer claims and refuses any two that coincide,
  and the tests cover each pairing that can occur.
- **YAML eats property maps.** `match: (c:CLAIM {role: 'thesis'}) …` is not
  YAML: `role: ` inside a plain scalar reads as a key. Fold (`>-`) or quote
  any pattern with a property map. The failure arrives as a YAML parser
  error before luria sees the config.
- **Navigation was already decided.** On nucleation the lint failed with
  "missing index entry for unopposed.md": `check_docs_index` wants every
  page directly under `docs/` listed in its README. So the record links its
  pattern pages, and the lint holds it to that.
- **`luria new changelog --name <branch>` hands back an existing path.** On
  a branch reused after a merge, that is the previous PR's uncollected
  fragment, and a shell redirect overwrites it. This PR's fragment is
  `pattern-pages-373.md`.

Tried on a scratch copy of nucleation's `main` (cf318d525, network off).
With no pattern `output`, `luria index` wrote the same files and `luria
lint` printed the same lines under luria `main` and this branch. With
`unopposed` and `undercut` added, 286 of 361 theses are unopposed and 8
(argument, Active claim) rows cover 6 arguments; a script reading the
frontmatter found the same sets. The counts moved from the first trial's
115 of 175 because nucleation's record grew in between.

**Follow-up, not done here:** `pattern_row/4` (what views read) and
`pattern_node/4` (what the `report: true` classes read) are two encodings of
one match, named and positional. The page and the class agree on the test
that pins it, but one shown predicate both could read would remove the
chance that they ever stop agreeing.
