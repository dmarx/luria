[#373](https://github.com/dmarx/luria/issues/373) gives a named pattern a page of its matches ([ADR-tmpgicpu](../../record/decisions.d/ADR-tmpgicpu.md)). The code is
small: the lowering already derived every match as `pat<k>_m(…)`, so
showing `pattern_match(P, (X, …))` and teaching `logic._python` that a
nameless clingo function is a tuple was the whole of the rules side. The
renderer is `luria/pattern_reports.py`, beside `chains.outputs` in
`adr_index.outputs`.

Three things worth not rediscovering:

- **YAML eats property maps.** `match: (c:CLAIM {role: 'thesis'}) …` is not
  YAML: `role: ` inside a plain scalar reads as a key. The issue's own
  examples were written that way. `test_no_example_is_still_written_in_toml`,
  which parses every YAML block in the configuration reference, caught it in
  the first docstring. Fold (`>-`) or quote any pattern with a property map.
  The failure arrives as a YAML parser error before luria sees the config,
  so luria cannot word it better without reading the file itself.
- **Navigation was already decided.** On nucleation the lint failed with
  "missing index entry for unopposed.md": `check_docs_index` wants every
  page directly under `docs/` listed in its README, and chain pages have
  always been linked there by hand. So the issue's question of whether the
  site should list pattern pages answered itself: the record links them, and
  the lint holds it to that. Fired once on that real case before writing
  that down.
- **Collisions were unchecked for every view, not only these.** Nothing
  refused two views rendering to one path. The check added here covers a
  pattern's `output` against schemes, status reports, chains and other
  patterns. A chain colliding with a scheme is still unchecked. Out of scope,
  but worth an issue if it ever bites.

One trap of my own making: `luria new changelog --name <branch>` hands back
the path of a fragment that already exists, which on a branch reused after a
merge is the previous PR's uncollected entry. Writing to that path with a
shell redirect overwrote it, and `git status` showing the fragment as
modified rather than new was the only sign. This PR's entry is
`pattern-pages-373.md`. Whether `luria new` should refuse an existing
fragment is a separate question.

Tried on a scratch copy of nucleation's current `main`. It already declares
`argued_from` with no output, so the parity run doubled as the "no `output`,
no change" check: index and lint (network off) were identical against luria
`main`. With `unopposed` and `undercut` added:

- 115 of 175 theses are unopposed;
- 8 arguments are undercut by an Active claim.

A separate script reading the frontmatter got the same numbers. Its ninth
undercutting claim, CLAIM-004 against ARG-004, is Proposed, and the property
map left it out as it should. The reference report did not change, so the
`is_generated` exclusion holds.
