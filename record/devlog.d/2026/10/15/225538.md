Phase 1 of [ADR-130](../../record/decisions.d/ADR-130.md) is the `views` family: a Jinja template rendered
by `luria index`. Its context is `doc`, `docs`, `vocabulary`, `schemes` and
`journals`. Before trusting it ([DP-006](../../record/principles.d/DP-006.md)), I fired it on two real cases, each
in a scratch copy.

**nucleation's `CLAUDE.md`, as a template.** I stripped every hand-written
link back to its bare code, `ANTH-LIT-285` and the other remote codes
included, and replaced "Where things are" with a loop over `schemes()`. The
render matched the committed file byte for byte outside the templated
section: the fixer re-linked every code, local and remote, exactly as it had
been written by hand. Rendering took 0.4 s on nucleation's 3,100 documents.
The firing found two gaps, both now closed. `schemes()` lacked the scheme's
`title` and `blurb`, and the journal directories (`workbench.d`,
`curation.d`) could not be listed. That is what `journals()` is for.

**A broken template in luria's own record.** A view citing `ADR-999` failed
`luria lint` with exit 1 and the line
`views.x: record/views.d/x.md.j2:5: ADR-999 names no document in this record`.
With the line removed, the view rendered, `luria index --check` reported it
current, and the existing docs-index rule asked for its entry in
`docs/README.md`. A view under `docs/` is held to what any page there is.

**Traps found along the way:**

- `trim_blocks` eats the newline after `{% endfor %}`. That is Jinja's
  documented behaviour and the right default for markdown built from
  loops, but a one-line loop needs `join` or an explicit newline.
- The lint renders every view to find the broken ones, and at first it
  rendered each working one twice, once for the view tree and once for the
  check. `views.errors(rendered)` now re-renders only the views missing
  from the tree the lint already built.
- `test_a_generated_view_is_utf_8_whatever_the_console_is` runs luria in a
  subprocess with `HOME` replaced. A dependency installed only in the user
  site (`pip install --user`) is invisible there, so the test fails with
  `ModuleNotFoundError: jinja2` on a machine where everything else passes.
  CI installs the package properly and never hits this.

**`match()`, fired on nucleation's argument graph.** The inline pattern
`(c:CLAIM)<-[:concludes]-(g:ARG)-[:rests_on]->(p:CLAIM) WHERE NOT
(g {status: 'Rejected'})` and the declared `argued_from`, which is the same
pattern, return the same five rows. Among them is CLAIM-027 through ARG-009
from CLAIM-080, which is the claim's own `rests_on` in its frontmatter.
Without the `WHERE NOT` there are six. The sixth row goes through ARG-004,
which is Rejected, so the negation does its job. The first `match` in
a process took 7 s, nearly all of it building the record's facts. That is
the cost `luria index` already pays on nucleation for its pattern chains.
Each further pattern took about 0.3 s, one solve of `relations.lp` with the
pattern added.

The existing lowering could not serve a view as it stood. `pattern_edge`
gives a match's two ends and `pattern_via` its named inner nodes, each
keyed by the ends alone. Two matches sharing their ends but passing
through different inner nodes therefore cannot be told apart, and a row
cannot be rebuilt from them. `pattern_row` keys each named node by the
whole match instead, and is generated only when a view asks for it.

**Phase 3, fired on nucleation.** The template transcluded every claim on
the `will-organization` line. It read 28 claims: 14 Proposed, 11 Active,
2 Superseded and 1 Rejected. `retired-transclusions` reported the two
Superseded ones at line 6, the loop body: CLAIM-012 (by CLAIM-027) and
CLAIM-062 (by CLAIM-080). A separate read of CLAIM-012 at line 10, with
`inactive-ok:` on the line above, was excused. The site's "Rendered into"
for CLAIM-012 named `docs/probe.md`. The count is why retirement here is
`retires_on` and not the citation scan's "not Active": the scan's rule
would have reported 17 of the 28.

Siting a read needed no tracking of my own. Jinja compiles a template into
Python whose module globals hold `__jinja_template__`, and
`Template.get_corresponding_lineno` maps a compiled line back to the source
line. Walking up from the read to the first frame that carries one finds
the innermost template, an `include`d file included.

Phase 1 had a gap that this phase found. A view's output was not
`is_generated`, so the citation scan read the rendered `CLAUDE.md` and
would have reported a retired code there, in a file the next build
overwrites. Chain pages are excluded for the same reason, and view outputs
now are too.

**Phase 4, fired on nucleation through the CLI.** A pinned view quoted
ARG-003's "The inference" and named the claim it concludes.
`luria views --pin paper` endorsed two documents, ARG-003 and CLAIM-086.
I then reworded the quoted inference. `luria views` showed the view as
drifted, the lint row named ARG-003, and `luria index` left the published
sentence in `docs/paper.md` untouched. After re-endorsing, I reworded a
line under "Critical questions", which the paper does not quote, and
there was no drift. That second edit is the reason the lock hashes the
values each document was read for and not the document's file: hashing
the file would have reported it.

Naming trap: the CLI's flag is `--pin`, and Fire maps a flag to a
parameter of the same name. So the module function could not also be
called `pin` without the parameter shadowing it inside `run`. It is
`endorse`.
