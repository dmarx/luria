Phase 1 of [ADR-tmpi08sj](../../record/decisions.d/ADR-tmpi08sj.md) is the `views` family: a Jinja template rendered
by `luria index`. Its context is `doc`, `docs`, `vocabulary`, `schemes` and
`journals`. Before trusting it ([DP-006](../../record/principles.d/DP-006.md)), I fired it on two real cases, each
in a scratch copy.

**nucleation's `CLAUDE.md`, as a template.** I stripped every hand-written
link back to its bare code, `ANTH-LIT-285` and the other remote codes
included, and replaced "Where things are" with a loop over `schemes()`. The
render matched the committed file byte for byte outside the templated
section: the fixer re-linked every code, local and remote, exactly as it had
been written by hand. Rendering took 0.4 s on nucleation's 3,100 documents.
The firing found two gaps, both now closed. `schemes()` lacked the scheme's
`title` and `blurb`, and the journal directories (`workbench.d`,
`curation.d`) could not be listed. That is what `journals()` is for.

**A broken template in luria's own record.** A view citing `ADR-999` failed
`luria lint` with exit 1 and the line
`views.x: record/views.d/x.md.j2:5: ADR-999 names no document in this record`.
With the line removed, the view rendered, `luria index --check` reported it
current, and the existing docs-index rule asked for its entry in
`docs/README.md`. A view under `docs/` is held to what any page there is.

**Traps found along the way:**

- `trim_blocks` eats the newline after `{% endfor %}`. That is Jinja's
  documented behaviour and the right default for markdown built from
  loops, but a one-line loop needs `join` or an explicit newline.
- The lint renders every view to find the broken ones, and at first it
  rendered each working one twice, once for the view tree and once for the
  check. `views.errors(rendered)` now re-renders only the views missing
  from the tree the lint already built.
- `test_a_generated_view_is_utf_8_whatever_the_console_is` runs luria in a
  subprocess with `HOME` replaced. A dependency installed only in the user
  site (`pip install --user`) is invisible there, so the test fails with
  `ModuleNotFoundError: jinja2` on a machine where everything else passes.
  CI installs the package properly and never hits this.
