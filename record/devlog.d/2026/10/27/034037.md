**A downstream record kept seeing stale reds from the pull-request shape ([ADR-068](../../record/decisions.d/ADR-068.md)).** Nucleation adopted a working rule of pushing each commit to its pull request as it is made, with CI as the check. Twice in one day, nucleation#334 and [#338](https://github.com/dmarx/luria/issues/338), a `docs-check` run went red on a commit that the next run passed. Every violation was a bare code or a missing converse, which is exactly what `luria repair` fixes.

The cause is in the generate action. The pull-request step commits the repair, then runs `git pull --rebase` so that the push lands on a branch that may have moved. When it has moved, the rebase brings the newer push's commits into this run's tree, unrepaired. The lint then runs in the same job, on that tree, and reports them. The newer push's own run repairs them a few minutes later, so the red is always stale. It still reads as a failure, and in a large record it costs a full run.

The fix repairs again when the rebase brought commits in. The step remembers the commit it checked out, and if that is no longer the parent of its repair commit after the rebase, it runs `luria repair` once more and commits the result before pushing. The lint then reads a tree in which every commit is repaired. The push can still race a third push, but that window is the seconds between the rebase and the push, not the length of a run.

A project can also cancel overtaken runs with a concurrency group, as nucleation now does. That saves the run, but it does not fix the action: a project without the group, or a push that lands after the lint has started, still hit the race. Fired before trusting ([DP-006](../../record/principles.d/DP-006.md)): against a scratch remote with a stub `luria`, a newer push landing during the run left the old step pushing a tree with one of the two files unrepaired. The new step repaired both and pushed two repair commits.
