title: 'Lint on a 5,500-file record spent four minutes on one regex, and the thread pool hid where the rest went'
created: '2026-10-28T08:27:06'
tags: []
---

**`luria lint` took about ten minutes on dmarx/nucleation.** Timed with the network off (`lint.network: never`, so upstream answers cannot vary the output), it was 614s on 5,519 scanned files. It is now 145s, and the lint's output is byte-identical to `main`'s.

**The profile to take is a serial one.** `py-spy record --idle --threads` on the pooled run said the chain pages took 86s and that `facts.fingerprint` took 52s of that. Run alone, the chain pages took 5s and the fingerprint under half a second over 13 calls. The rest was waiting for the interpreter lock. Almost everything in lint is CPU-bound Python, so the render pool overlaps nothing: `LURIA_JOBS=1` took 146s and the default width 150s. A pooled profile attributes lock waits to whatever frame was waiting, so it accuses the wrong code. `LURIA_JOBS=1 python -m cProfile` gives an honest one, as `parallel.py` says.

**The wrong first theory was the logic core.** The owner suspected the record's facts were rebuilt on every ask. They are not. `facts()` is memoized, and a lint builds them twice (about 36,000 and 42,000 facts, about 2s each). Every `derive()` call re-stats every document to prove nothing changed, but that costs under 0.1s a call when nothing else is running. The whole logic path, facts and solves together, was about a tenth of the run once the larger costs were gone. Caching facts across runs would save seconds, not minutes.

**Most of the time was one regex.** `bibliography._LEAD_RE` reads an author-year lead. Its name pattern and its joiner overlap: `A.` is both a surname and an initial, and a run of commas and spaces splits several ways. Its run of names is capped at 40. A 26-author entry, `LIT-1357`'s, has more than 50 name tokens, so the match must fail, and the engine tries every split first. That block alone took 254s, and `re` holds the interpreter lock while it matches, so every other thread stalled too. That is why the solves showed 23s of wall time against 2s of CPU. Making the run possessive (`{0,40}+`, Python 3.11+) commits to the longest run of names, and a failing lead fails in linear time. Against 342,529 blocks in nucleation and luria, old and new leads differ on two. Both are `F2013 and F2016`, which the old pattern read as `F2013 and F`, published in 2016, by giving back the digits of a name. `is_entry` gives the same answer for both.

**The rest was per-character Python and repeated work:**

- `doc_refs.masked` and `find_refs` set flags one character at a time, and `_line_index` walked every character to find newlines. Slices and `bisect` do the same in C.
- `find_refs`, `legacy_spellings` and `ref_status._scan` ran two regexes per scheme over every file, about 77 passes on nucleation. A leading `\b` stops `re` from searching for the literal prefix first, so each pass cost the same whether or not the prefix was there. A substring test now skips a scheme whose prefix is absent. It is exact only for a prefix with no regex metacharacters, so it is applied only then.
- `ref_status._scan` ran those passes once per line. Codes never span a line break, so it now matches the whole text and files each code by line, with the line breaks `str.splitlines` uses. A test pins that a form feed and U+2028 count as `splitlines` counts them. It passes on `main` as well.
- `contract.resolvable` rebuilt a scheme's whole code set for each of 38,000 asks: 26 million `Scheme.code` calls. It is now held against the identity of the scheme's cached listing, so a new listing is a miss.
- `is_generated`, `is_historical` and `link_base` compared each path against every view, vocabulary directory and journal on every call, through pathlib's slow `__eq__`. They now index the config once, in `cached_property`s on `Config`, which is never mutated after it is built.
- `lint.status_sections` called `ref_status.scan(docs=docs)`, which bypasses the corpus-scan cache. So every lint scanned the corpus twice. `reports.reference_status` had the same bug fixed before, and that comment says why.

**Not done, and where the remaining time goes.** Of the 145s, the reference report's corpus scan, the bare-reference scan and the annotation survey each read every file and build their own masks. `load_scheme` constructs about 107,000 `Adr` objects in a run, each with a deep copy of its frontmatter, because readings are per-object on purpose ([#233](https://github.com/dmarx/luria/issues/233)). Caching a whole scheme's load across a run would be a design change, not a refactor. If changes stay localized, the next large step is per-file results cached across runs, keyed on a file's content and the config. A fact cache alone would not be it.
