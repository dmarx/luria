**The problem.** Nucleation promoted 53 readings in status review 22. It
then cleared the stale acknowledgements with a throwaway script, which
changed 47 directive lines in 46 files (its commit `23de5f786`). Taking an
Active code out of an `inactive-ok` has one correct answer, so it now
belongs to `luria repair` (ADR-tmpbu1p0).

**The lint only saw part of it.** `stale_annotations` judged each directive
as a whole: a directive was stale when it excused nothing. Of the hand
trim's 47 lines, the lint had reported 21. Another 25 were in directives
whose other codes still excused citations, so the dead Active code in them
was never reported. One more was in a workbench journal entry, which the
reference scan treats as historical and never reads. A repair limited to the
reported directives would have missed over half the case. The lint now has a
second row for an Active code inside a used directive, and both the row and
the repair read `ref_status.settled_codes`.

**Fired on the real case.** I extracted Nucleation at `0d244a39d`, the
parent of the hand trim, with `git archive` into a scratch directory and ran
this branch's luria against it.

- Before: 1476 stale-directive rows from the reference scan. 499 were the
  existing "X is Active now" rows and 977 were the new per-code rows. So
  Nucleation was carrying about 1,400 such directives beyond pass 22's.
- `luria repair`: 1476 directive lines in 1336 files, 1001 rewritten and
  475 deleted. Every removed code names an Active document.
- After: 24 rows, all "nothing in scope cites". Those need a person, and the
  repair leaves them.
- A second `luria repair` reported `repaired 0 file(s)`.
- Against the hand trim, the repair made every removal it made, except
  `THEORY-927` in `record/workbench.d/2026/10/25/043048.md`. That file is
  historical to the scan, so the lint never reported it either. In the other
  35 differing files, the repair also removed older Active codes the script
  was not looking for, such as `QUESTION-277`, which is `Open`, the QUESTION
  scheme's in-force status.

**Traps.**

- The directive parser's `span` starts at the comment, not at the
  directive's name. That is `<!--` in markdown and `#` in Python, and in
  frontmatter it is the character after `#`. So the rewrite searches for
  `<name>[-scope]:` from that offset rather than trusting the span.
- An `until <date>` expiry lives among the arguments as two tokens and must
  survive a comma-separated rewrite as one phrase.
- When a directive shares its line with another comment, as in
  `<!-- inactive-ok-block: X --><!-- unexempt-block: codeblock -->`, only
  that comment is removed, not the line.
- Test fixtures put their citations in backticks. Otherwise `luria repair`
  links them in the same run, and a whole-file comparison fails for a reason
  that has nothing to do with the trim.
