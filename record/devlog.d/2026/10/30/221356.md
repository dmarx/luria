A converse pair can now mark one side `derived: true`. Only the other side,
the primary, is stored, and `luria repair` moves anything written on the
derived side ([ADR-tmpwpas9](../../record/decisions.d/ADR-tmpwpas9.md), superseding [ADR-084](../../record/decisions.d/ADR-084.md) for directed pairs). The
owner asked for this on [DP-002](../../record/principles.d/DP-002.md) and [DP-003](../../record/principles.d/DP-003.md) grounds. A second ADR,
[ADR-tmpu2wwj](../../record/decisions.d/ADR-tmpu2wwj.md), states which command a write like this belongs in.

**Readers needed no change.** `relations.edges()`, `held/4` in
`luria/logic/relations.lp`, already unions a relation with its converse, and
chains, invariants, patterns, reliance and the site all read through it. So
removing a stored derived side loses nothing any of them sees. This was
checked rather than assumed: `held/4` over the Nucleation copy had 10,815
tuples before normalization and the same 10,815 after, compared with `diff`.

**The normalization is a logic program, `luria/logic/normalize.lp`, beside
`converse.lp`.** `converse.lp` now restricts its `pair/4` to pairs with no
derived side, so [ADR-084](../../record/decisions.d/ADR-084.md)'s HEAD-relative completion runs only for symmetric
and undirected pairs. The two programs never claim the same pair.
`ref_derived/2` is a new schema fact, read by `consistency.lp` too: a pair
with both sides derived, `derived` without a converse, and `derived` on a
self-converse relation are refused when the configuration loads.

**A move is judged as one unit.** It is an add on one document and a removal
on another. Through `relations._blocked` the contract could refuse the add
and allow the removal, and applying the halves separately would lose the
edge. So each move is checked whole. The survivors are then checked again
as the batch they will be written in, because two moves that are each safe
can together break a field group in one file.

**Removal goes by the resolved code, not the spelling.** A derived entry
written as a readable alias (`LIT-origin`) has to be removed in that
spelling. `_drop_code` reads the field, resolves each raw value through
`reference_code`, and drops the ones that land on the code being moved. The
add writes `readable(code)`, the spelling a person would choose, as
completion already did.

**Fired on a `git archive` of Nucleation's default branch** (2e046bf6c), in
the scratchpad, with `derived: true` added to 28 reference fields, chosen as
the dependent→dependency reverses. They match every blurb in Nucleation's
configuration that reads "written by `luria link --fix`".

- Before: `one-sided-relations` 812 rows, `undirected-relations` 36 pairs.
- `luria repair`: 2,626 drops and 62 moves, 1,256 files changed (4,228 lines
  out, 105 in). Nothing was held back by a contract, no clash, no dangling
  entry. Every changed file was a normalization; no other repair fired. 45
  seconds.
- Second `luria repair`: "repaired 0 file(s)".
- After: `luria lint` clean, `one-sided-relations` 79 rows (all symmetric:
  `compared_against`, `rivals`, `complements`), `undirected-relations` gone.
  The unverified-identifier count moved from 312 to 398 between the runs.
  That was arXiv returning HTTP 429, not this change.
- The 62 moves: 55 `corroborated_by` to `corroborates`, 4 `illustrated_by`
  to `illustrates`, 2 `supports` to `grounds`, 1 `refined_by` to `refines`.
  Five were checked by hand (CASE-018/CLAIM-091, CLAIM-136/THEORY-032,
  QUESTION-030/QUESTION-284, CLAIM-156/CLAIM-349, THEORY-047/CLAIM-356); each
  derived entry became the primary entry on the other document.

**One data point the hand check turned up.** THEORY-032 both `supports`
(derived from `grounds`) and `corroborates` CLAIM-136, which Nucleation's
own decisions treat as different relations. Normalization moved
both faithfully, since both were already in `held/4`. Which one is meant is
a question for that record, not a repair.

**`luria relate` had been saying `luria repair` writes the converse.** It
never did: completion was only ever in `link --fix`, and a test pinned the
false sentence. The note now says which of the three cases applies, through
a new `relations.direction()`.

**The repair.py change is one self-contained block**, placed after the status
repairs, because the open PR [#389](https://github.com/dmarx/luria/issues/389) also edits `repair.apply`.
