**The question.** The owner asked whether clingo is still the right engine
for luria. dmarx/nucleation had needed two things the pattern subset could
not say. One was three near-identical reported patterns, for a note status
against three LIT statuses; [ADR-135](../../record/decisions.d/ADR-135.md)'s `IN` covers that on `main`, but
not in 1.6.0. The other was a grouped count, for candidate `line:` values
inferred from the graph, which had to be run in SQL over `luria export`.
The hypothesis: DuckDB with the DuckPGQ extension speaks SQL/PGQ, whose
`MATCH` is GQL's pattern language, so luria could stop writing its own
lowering. [ADR-127](../../record/decisions.d/ADR-127.md) rejected Cypher, embedded graph databases and
SQL CTEs. This entry tests that rejection; it decides nothing.

**What was built** (`experiments/duckdb_pgq/`, outside the package; nothing
in `luria/` changed):

- `load.py` puts the facts `luria.facts.facts()` hands clingo into DuckDB,
  one table per predicate, so both engines read identical input.
- `rules.sql` ports `relations.lp` and `invariants.lp`, rule for rule, as
  views.
- `patterns.py` lowers luria's parsed `Pattern` to a DuckPGQ `GRAPH_TABLE
  (… MATCH …)` query.
- `compare.py` and `compare_patterns.py` diff every derived atom against
  `logic.derive`.

**Fired on** a nucleation checkout at main after its PR 386, which has 6,058
documents, 164,079 facts and 11 declared patterns. It was also fired on a
scratch copy of that checkout with `invariant:` added to `LIT.extends`
(tags) and `CLAIM.rests_on` (line), so that `unbound_relation` is
non-empty: 51 pairs. Sixteen synthetic patterns reach the grammar's corners:

- variable length `*1..3`, `*2..3`, `*`, `*2..`, `*3..` and `*2..2`;
- a left-pointing variable hop;
- `|`, `IN`, `<>` and `NOT … IN` on a multi-valued field;
- a back-reference closing a cycle, `WHERE NOT` on a path, and a via node;
- a 30,237-pair closure over the symmetric `complements` relation.

**Result: everything matches, after five workarounds.** `held` (11,397),
`unbound_relation` (0; 51 on the scratch copy), `unbound_edge` (52),
`unbound_line` (6), `member` (1,039) and `pattern_edge` (129) are identical.
All 27 patterns are identical, match for match and position for position.

**DuckPGQ's departures from SQL/PGQ, each reproduced on a toy graph:**

1. **Quantifiers are shortest-path, not walk.** On a→b, a→m, m→b,
   `-[e]->{2,2}` returns nothing, under the default mode, `ALL` and
   `ANY SHORTEST WALK` alike, though a→m→b is a walk of length 2. A pair
   matches `{lo,hi}` only when its shortest path length is in range.
2. **The same breaks cycles.** On a→b, b→a, `{1,3}` omits (a,a), because
   the shortest path from a node to itself has length 0.
3. **`{0,1}` drops its zero-length matches**, though `{0,2}` keeps them.
4. **A quantified left-pointing edge is not implemented** ("Cannot do
   shortest path for edge type MATCH_EDGE_LEFT").
5. **`|` between labels does not parse.** Every edge must be named
   (`[e:f]`, not `[:f]`), and every node labelled, a back-reference included.

The lowering works around all five:

- a bounded hop is unrolled into `low` steps over the edges, then
  `high - low` steps over an "opt" edge table that adds a self-loop on
  every document, so each step is zero or one. No quantifier is used, and
  walk semantics hold by construction;
- an unbounded hop is unrolled into `low` steps, then `*` under `ANY
  SHORTEST`. Zero or more steps exist iff a shortest path does, so the
  shortest-path reading is exact there;
- a left variable hop reads a reversed edge table;
- a hop with several fields reads an edge table that is their union.

So luria would still write a lowering. It would be smaller than the clingo
one, but it would be shaped by the engine's bugs rather than by the
grammar.

**The version trap.** DuckPGQ loads on DuckDB 2.0.0, but its syntax does
not parse there: `CREATE PROPERTY GRAPH` fails at `PROPERTY`. It works on
1.5.6. On 1.5.6, `invariants.lp`'s `common` rule, written as a doubly nested
correlated `NOT EXISTS`, returned 308 rows where 302 is right. The
anti-join against that view then returned 308, while `EXCEPT` and an
anti-join against a materialized copy of the same view returned 0. DuckDB
2.0.0 returns the right answer for every form. The port now writes `common`
as a grouped count, which is clingo's own `#count {…} = 0`, and is right on
both versions. The graph syntax needs 1.5.x, and 1.5.x got this query
wrong. The bug was not minimized and is not filed upstream.

**[ADR-127](../../record/decisions.d/ADR-127.md)'s objections, revisited:**

- *"Rules do not compose by name"* (SQL CTEs). Views do: `rules.sql` names
  `reads`, `held`, `near`, `reach`, `member` and `common` and builds each on
  the last, as the `.lp` files do. The SQL is longer: 84 non-comment lines
  against 32 for the two `.lp` files. Readability is the owner's call.
- *"The embedded options are heavy for a lint CLI."* This holds. clingo is
  about 7 MB installed. DuckDB's binary is 60–68 MB, and DuckPGQ is 33 MB
  more. DuckPGQ is also a community extension, fetched from DuckDB's
  extension repository on first `LOAD`: a network fetch in a lint run, at
  a version pinned to the core's.
- *Speed* is not the issue on either side. Warm, best of 3, on 4 cores:

  | workload | clingo | DuckPGQ |
  |---|---|---|
  | the record's 11 patterns | 0.28 s | 0.03 s, plus 0.06 s graph build |
  | with the 16 synthetic patterns | 2.28 s | 2.36 s |

  The DuckDB load takes 0.33 s, and `luria.facts` builds the facts in
  3.3 s, which dominates both engines.

**Not covered:** `acknowledgements.lp`, `consistency.lp`, `converse.lp`,
`reliance.lp` and normalisation, which are four of six rule files plus one
more; luria's own record and the anthology; and luria's test fixtures. The
semantics were matched to `pattern_rules.py` at b93078e.

**Where this leaves the question.** Two things were tangled together:

- *A query surface people know.* Plain SQL over the same fact tables, on
  DuckDB 2.0.0, ported the rules with no wrong answers once `common` was
  rewritten. It needs no DuckPGQ. A read-only query command could rest on
  it without touching lint.
- *Replacing clingo for lint.* DuckPGQ is not ready to carry lint today: it
  is blocked on 2.x, its quantifiers are not walk semantics, and it adds a
  network fetch. Nor would it remove luria's lowering. A GQL front end would
  lower to SQL instead of clingo, so a parser change and an engine change
  are separate decisions.

Rerun: `python3 -m compare` and `python3 -m compare_patterns` from a
record root, with `PYTHONPATH=<luria>:<luria>/experiments/duckdb_pgq` and
`duckdb<2` (see the experiment's README).
