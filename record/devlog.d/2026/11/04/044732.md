`luria unconcretize CODE...` (`luria/unconcretize.py`, [ADR-140](../../record/decisions.d/ADR-140.md)) gives a
numbered document its number back as a temporary code.

**Fired on the real case before trusting it.** The case was nucleation#387,
whose branch filed `ADR-068` while the trunk merged a different `ADR-068`. In a
scratch worktree of that branch:

- `unconcretize ADR-068` renamed it `ADR-tmpuzsbf` in about 3 seconds and
  rewrote three files: the document's heading, `luria.yaml` (five comments
  and blurbs) and a changelog fragment, whose link label and target both
  changed.
- After a commit, `git merge origin/main` was clean. The add/add conflict
  was gone.
- `concretize` then numbered the document `ADR-069`, recorded `formerly:
  ADR-tmpuzsbf`, and rewrote all five `luria.yaml` citations.

**Traps.**

- **`concretize` never rewrote `luria.yaml`.** A temporary code cited in a
  config comment survived concretization as a dangling code. The fix is
  one file list, `concretize.rewritable_files`, which both commands read,
  config included. The fired case found it: before the change, `ADR-069`'s
  five config citations would have stayed `ADR-tmpuzsbf`.
- **Plain replacement is safe for a temporary tail and wrong for a
  number.** `LIT-156` is a prefix of `LIT-1563`, and nucleation has
  four-digit codes. The match is whole-token, and excludes a preceding `-`,
  so `LU-ADR-068` is not touched.
- **Giving back several numbers in one commit ties them** for concretize's
  commit-time order. The renumbering test asserts contiguity and survival,
  not which document takes which number.
- **The first design scoped the rewrite to lines added since a merge
  base.** It refused mid-merge, and refused documents that predate the
  branch. The owner rejected it: the user names the document, and the
  command should not be relative to a commit. Running before the merge
  gives the collision fix without it.
