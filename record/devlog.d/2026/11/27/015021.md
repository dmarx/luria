**What moved.** [ADR-tmpg4gc4](../../record/decisions.d/ADR-tmpg4gc4.md)'s first step. `journal.render_book` now
renders `luria:journal-book.md.j2` over `journal.book_context`. The data
half still lives in `journal.py`: which entries, the period label, and each
entry's heading slug.

**The slug pass is why there are two template files.** The contents list
links each entry heading's slug, and a slug depends on every heading before
it in the book, entry bodies included ([ADR-100](../../record/decisions.d/ADR-100.md)). So the slugs are computed
from rendered markup. Keeping a Python copy of the section markup for that
pass would have been two copies to drift ([DP-004](../../record/principles.d/DP-004.md)). Instead the section and
heading markup are macros in `luria:journal-book-parts.md.j2`, which the
book template imports and `entry_anchors` renders. They had to be a
separate file: Jinja's `template.module` renders the importing template's
top level with an empty context, and the strict undefined rejects that.

**How "unchanged" was checked.** `tests/test_journal_book_view.py` keeps
the old generator verbatim as an oracle, helpers included. The first draft
of the oracle called `journal._sections` and `journal.entry_anchors`, so
for everything below the contents list it compared the new code with
itself. It passed first time, which is what gave it away. A positive control
now changes one field of the shipped section and asserts the comparison
notices ([DP-015](../../record/principles.d/DP-015.md)). The oracle matched on every book of four real records:

| record | books | entries |
|---|---|---|
| luria | 4 | 162 |
| nucleation | 6 | 525 |
| strata-g | 3 | 78 |
| mantle | 1 | 3 |

On this branch, `luria index` changes the November book only by adding this
branch's own unmerged entry.

**The cost, and the fix.** Rendering through `views._environment()`
compiled three templates per book, plus the parts once per call, because
that environment is deliberately rebuilt per render: a project's template
is read from the tree as it is now. On luria's 162 entries that was 0.071 s
against the generator's 0.008 s, about 9×. A shipped template is read from
the package, which doesn't change under a running process, so
`views.shipped(name)` compiles each once per process, with the same
sandbox, undefined and filters. Best of five runs after the change: 9.8 ms
against 7.1 ms. Worth knowing for every later step of the migration: **use
`views.shipped`, not `_environment()`, for a `luria:` template rendered
in a loop.**
